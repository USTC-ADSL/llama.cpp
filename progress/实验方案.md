# 实验计划 025：请求长度与 SLO 感知的 PD（Prefill / Decode）调度实验

> **归档说明**：上一版以 `split-stage / mixed-route` 为核心的实验方案已归档到 `progress/2026-03-25-038-stage-split-plan-archive.md`。  
> **本版修正说明**：这里的 `PD` 明确指 **`Prefill` 与 `Decode` 两个 phase**，不是 `Power Domain` 或 `Processing Domain`。  
> 因此，本版实验方案的主调度粒度统一改为 **phase-level**：只在 `Prefill -> Decode` 边界做后端 / workpoint 选择，而不再把 `Decode` 内部继续细分成 block-level 或 stage-level 作为主方向。
>
> **当前工作假设**：  
> 1. 不同请求长度（`prompt_len`, `gen_len`）会改变 `Prefill / Decode` 的占比，从而改变不同 backend 的适配性；  
> 2. 在固定请求长度与 phase 后，不同 backend / workpoint 之间存在可利用的 power-tunable space；  
> 3. `split-stage` 之所以没有兑现收益，主要是因为粒度过细，导致 runtime overhead 无法被摊薄；  
> 4. 因而，当前最值得验证的不是更细粒度切图，而是围绕 **请求长度 × SLO × PD phase** 建立调度与降功耗策略。

## 0.5 2026-03-26 当前最新状态（建议先读）

> 当前文档较长，且包含多轮历史诊断。  
> 若只关心“现在做到哪一步、哪些结论已经作废、接下来补什么实验”，优先读本节，再读 `7-C` 与 `9`。

### 0.5-A：当前主线已进一步收敛

当前实际主线已经不是“继续探索 split-stage / mixed-route”，而是：

- **只做 `Prefill / Decode` phase-level 的静态后端切换**
- 当前最核心的真实路径是：`Prefill = qnn-npu(full)`，`Decode = GPUOpenCL`
- 重点不再是“有没有 phase 偏好差异”，而是：
  - 当 `Prefill` 与 `Decode` 后端不同，真实 `KV migration / phase switch` 成本有多大
  - 这笔成本里哪些已经能消掉，哪些还需要继续拆

### 0.5-B：本周最新已验证结论

1. `split-graph` / `split-stage` 路线已明确退出主线。它们只保留为“粒度过细导致 runtime overhead 吞收益”的反证据。
2. `QNN full-graph prefill -> OpenCL decode` 的真实路径已经不再是 crash blocker。
3. 之前 decode 侧最大的问题不是 backend 本身不适配，而是 runtime bug 导致 decode token 在 `decode/base` 路由之间来回抖动；这一项已经修掉。
4. `full-graph QNN` 的 generic KV writeback 已实现，但又暴露出一个新的 runtime accounting 问题：
   - **修复前**：即使是 `QNN/QNN`，也会提前在 `Prefill` 阶段执行通用 KV writeback，导致同后端路径也白白多付一笔 `~94-101 ms`
   - **修复后**：`QNN/QNN` 已不再发生实际 KV migration
5. 当前又完成了第二步关键修复：
   - 原本写入通用 KV 的实际成本发生在 `QNN Prefill` 内部，因此被算进 `T_prefill`
   - 现在已经把**真正的通用 KV flush** 延后到 `Prefill 结束后、Decode route 切换前`
   - 并且在 timing trace 里新增了 `kv_migration_us`

### 0.5-C：当前最重要的最新证据

以下结果来自 `fd8657d6` 调试闭环，主要用于验证 runtime 行为与开销归因，不直接替代主设备功耗样本。

1. `QNN/QNN` 控制组证明：同后端路径不应该发生 migration。
   - 修 gate 前：
     - 静态 `QNN/QNN pp128+n0`：`666.43 tok/s`
     - 动态 `QNN/QNN wb=0`：`642.10 tok/s`
     - 动态 `QNN/QNN wb=1`：`436.59 tok/s`
     - 动态 `QNN/OpenCL wb=1`：`424.75 tok/s`
   - 这说明当时真正拖慢 `Prefill` 的不是 route skeleton，而是“本不该在 `QNN/QNN` 里发生的 generic KV writeback”
2. 修 gate 后：
   - 动态 `QNN/QNN wb=0`：`617.81 tok/s`
   - 动态 `QNN/QNN wb=1`：`615.43 tok/s`
   - 两者只差约 `0.80 ms`，可视为**当前 `QNN/QNN` 已无实际 KV migration**
3. 将通用 KV flush 延后到 phase switch 后：
   - `QNN/OpenCL pp128+n0` 回升到 `558.40 tok/s`
   - 说明原来记在 `Prefill` 里的主要 write-to-generic-KV 成本，已经被从 `T_prefill` 拿走
4. 真正串行的 `Prefill -> Decode` 口径必须用 combined workload，例如 `llama-bench -pg 128,1`，而不是分开的 `-p 128 -n 1`
5. 在 `-pg 128,1` 的 verbose trace 里，已经直接看到：
   - prefill: `kv_migration_us = 0`
   - 然后打印：`starting KV migration after prefill before decode route switch`
   - 再打印：`[aot] flushed deferred generic KV migration: pending_layers=28`
   - decode: `kv_migration_us = 78480`
   - 这说明当前 timing 口径已经从“把 migration 算在 prefill”切到了“显式 phase switch / decode-entry 成本”

### 0.5-D：当前哪些旧结论已经过时

- “`QNN/QNN` 下 generic KV writeback 没区别，因此当前实现没问题”  
  已失效。现在的证据相反地说明：修复前 `QNN/QNN` 确实被错误拖慢了。
- “当前主要问题还是 per-token route thrash”  
  已失效。这个 bug 已修掉；当前主问题已经收敛为：
  - `Prefill` 末尾仍保留的 payload staging / row assembly 成本
  - `Decode` 入口的真实 `KV migration`
  - decode steady-state 相对静态 OpenCL 的残余 orchestration 开销
- “用 `llama-bench -p ... -n ...` 就能直接看 phase switch 开销”  
  已失效。对 `llama-bench` 来说，`-p` 与 `-n` 默认会拆成独立 test；要看真实 `Prefill -> Decode`，必须用 `-pg`

### 0.5-E：当前最值得补测的实验

当前文档剩余实验里，优先级最高的已经收敛成四项：

1. **主设备重新测 combined phase path**
   - 在功耗主设备上，用修复后的 runtime 重测：
     - `pp128+tg1`
     - `pp128+tg16`
     - `pp128+tg64`
     - `pp512+tg64`
     - 如有时间再补 `pp512+tg256`
   - 统一使用 combined 口径，而不是分开的 `pp / tg`
2. **量化“剩余 Prefill 成本”**
   - 当前真正写通用 KV 的 flush 已经延期到 phase switch
   - 但 `QNN` 输出重新组装成 pending payload 的成本仍在 `Prefill`
   - 需要补一轮 `pp128+n0 / pp512+n0`，比较：
     - 静态 `QNN/QNN`
     - 动态 `QNN/QNN`
     - 动态 `QNN/OpenCL(deferred)`
   - 目标是把 “payload staging / row assembly” 单独估出来
3. **量化 `kv_migration_us` 的长度依赖**
   - 现在只有 `-pg 128,1` 的直接 trace 样本
   - 需要至少补：
     - `-pg 32,1`
     - `-pg 64,1`
     - `-pg 128,1`
     - `-pg 512,1`
   - 看 migration 是更像固定常数，还是随 prompt 长度近线性增长
4. **主设备功耗样本回填**
   - 之前主设备上的 phase-level 功耗样本大多还是“修 gate / deferred migration 之前”的口径
   - 这些样本不能直接拿来代表当前最新 runtime

## 0. PD 定义与研究目标

### 0-A：本方案中的 PD 是什么

本方案中的 `PD` 统一只指：

- `Prefill`
- `Decode`

也就是说：

- `PD-level scheduling` = 在 `Prefill` 和 `Decode` 两个 phase 上分别选择后端 / workpoint；
- **不包括**：
  - `Decode` 内部 layer block 切分
  - `attn_proj / attn_core / ffn` 这类 stage split

### 0-B：本方案要回答的核心问题

1. 对于不同请求长度 `Req = (prompt_len, gen_len)`，`Prefill` 与 `Decode` 分别更适合哪个 backend？
2. 在固定请求长度与 backend 后，是否存在足够的 `SLO slack`，允许通过降低 CPU/GPU/QNN workpoint 来降功耗？
3. 当 `Prefill` 与 `Decode` 的最优 backend 不同且 SLO 允许时，真实系统中的一次 `Prefill -> Decode` 切换开销是否足够小，能够兑现 phase-level Oracle？
4. 最终能否得到一个 `request-length × SLO -> policy` 的决策图，而不是只给出单一默认后端？

### 0-D：本方案中的 SLO 定义

本方案中的 `SLO` 不再写成抽象时延上限，而统一定义为：

- **相对该 workload 上最优 config 的允许降速倍数**

记：

- `w = (prompt_len, gen_len)` 表示一个 workload
- `P` 表示某个 config / policy
- `Perf(P, w)` 表示该 config 在 workload `w` 上的处理速度
- `Perf_best(w) = max_P Perf(P, w)`

则定义：

```text
SLO_factor >= 1
Perf(P, w) >= Perf_best(w) / SLO_factor
```

等价地，对于固定 workload，也可以写成时延形式：

```text
Time(P, w) <= SLO_factor * Time_best(w)
```

因此：

- `SLO_factor = 1.0` 表示必须达到该 workload 的最优速度
- `SLO_factor = 1.1` 表示允许比最优 config 慢 `10%`
- `SLO_factor = 1.25` 表示允许比最优 config 慢 `25%`
- `SLO_factor = 1.5` 表示允许比最优 config 慢 `50%`
- `SLO_factor = 2.0` 表示允许比最优 config 慢 `100%`
- `SLO_factor = 3.0` 表示允许比最优 config 慢 `200%`

后续文档中的 `strict / balanced / relaxed`，都应理解为不同的 `SLO_factor` bucket，而不是绝对时延门限。

建议当前实验优先使用以下 bucket：

- `strict = 1.0`
- `near-strict = 1.1`
- `balanced = 1.25`
- `relaxed = 1.5`
- `very-relaxed = 2.0`
- `energy-first = 3.0`

其中：

- `1.0-1.25` 更适合交互式、强响应要求场景；
- `1.5-2.0` 更适合允许明显降速但仍关注体验的场景；
- `3.0` 更适合作为“能否显著降 workpoint / 降功耗”的上界探针。

### 0-C：本方案默认不再优先做的事

- 不再把 `split-stage mixed route` 当作主实验方向；
- 不再把 `Decode` 内部更细的 block-level 或 layer-level 切分当作当前优先级；
- 不再用单个 stage 的 raw winner 去直接推导系统级收益；
- 不再把 `full vs split` 的差异当作主问题，而是把它们作为“细粒度开销过大”的反证据。

### 1-A：负载覆盖原则

本版 `PD` 实验默认必须覆盖多种上下文长度，而不是只看 `pp128 / pp512` 这类中等负载。

统一按三段 workload 看待：

- **小任务**：`pp16-pp64`，通常配合 `tg1-64`
- **中等任务**：`pp128-pp512`，通常配合 `tg64-256`
- **长上下文任务**：`pp1024-pp2048`，通常配合 `tg256-512`

这里特别强调小任务：

1. 小任务在真实手机交互里更常见，例如短问答、短摘要、短指令执行；
2. 小任务下 `Prefill -> Decode` 切换开销更难被摊薄，因此最容易暴露 phase-level 调度是否真的值得；
3. 若一个 policy 只在 `pp512+` 这类大任务上成立，而在 `pp16-pp64` 上被切换开销吞掉，则它不能被当作默认系统策略。

除此之外，必须区分四类代表性请求：

- `短 prompt + 短 decode`
- `短 prompt + 长 decode`
- `长 prompt + 短 decode`
- `长 prompt + 长 decode`

因为它们虽然都可以写成 `Req = (prompt_len, gen_len)`，但 phase 占比和可用 `SLO slack` 完全不同，backend 适配性也不应混为一谈。

### 1-C：本方案的决策目标

本方案最终不是只输出“某个 phase 用哪个 backend 更快”，而是输出三类结果：

1. **Backend affinity map**  
   对不同 `prompt_len / gen_len` 区间，判断 `Prefill` 与 `Decode` 分别更适合 `CPU / GPU / QNN` 中的哪个 backend。
2. **SLO-aware workpoint map**  
   在 backend 确定后，判断在给定 `SLO_factor` 下是否能把 `CPU policy / GPU devfreq / QNN n_hvx_threads` 下调而仍满足性能约束。
3. **Phase-switch trigger region**  
   只有当 `Prefill` 与 `Decode` 的 backend 偏好不同，且 phase 切换开销小于收益预算时，才触发 phase-level 动态路径。

### 1-B：QNN `n_hvx_threads` 记法修正

本方案中的 `hvx` 统一指 QNN 配置里的 `n_hvx_threads`，不是“物理 NPU core 数”。

因此：

- 现有 `hvx4 / hvx8 / hvx16` 数据，严格来说应解释为 `n_hvx_threads = 4 / 8 / 16` 的**历史配置点**；
- 不应把它们直接写成“4 核 / 8 核 / 16 核 NPU”；
- 若当前这台 `PKR110` 的可用 HTP/HVX 硬件并发上限实际为 `6`，则后续正式 workpoint sweep 应收敛到 `1-6`；
- 现有 `8 / 16` 结果只保留为**饱和 / 越界探针**，用于说明超过硬件并发上限后收益已基本饱和，不再作为正式 policy 空间。

### 3-C：为何这些负结果仍可复用

1. 它们说明当前高功耗**不是只有冷启动才能解释**。因为在 `tg512` 这种 sustained decode 下，split / mixed route 仍然停在 `3.9-4.8 W`，而静态 full-graph 只有 `~2.7 W`。
2. 它们说明当前主要瓶颈更像：
   - `split launch`
   - `sync`
   - `runtime contract`
   - `CPU orchestration`
   - `KV 管理`
3. 它们因此只保留为一个反证据：  
   **当前阶段级切图太细，不应继续作为主实验主线。**

### 3-D：本节直接结论

当前最合理的主线不是继续做更细的 stage split，而是：

- 先建立 `request length -> backend affinity` 的静态图谱；
- 再建立 `request length + SLO_factor -> workpoint relaxation` 的功耗图谱；
- 只有当 `Prefill` 与 `Decode` 的 backend 偏好明显分离时，才继续验证 `PD = phase-level` 的真实系统路径；
- 若 phase-level 仍显著留有未解释空间，再考虑是否值得回到更细粒度。

## 4. Phase-Level 候选策略与搜索空间

> 本节中的 phase-level policy 只是最终决策空间的一部分。  
> 更上层的目标是先得到 `request-length × SLO_factor -> backend/workpoint` 映射，再判断其中哪些区域值得启用 phase-level 动态切换。

### 4-A：新的调度对象

本方案只允许两类决策：

1. 为 `Prefill` 选择一个 `(backend, workpoint)`
2. 为 `Decode` 选择一个 `(backend, workpoint)`

也就是说，当前策略统一写成：

```text
Policy = (Prefill backend / workpoint, Decode backend / workpoint)
```

### 4-B：候选策略族

| 策略族 | 形式 | phase 切换次数 | 当前优先级 |
|--------|------|---------------:|------------|
| `S0` 静态单后端 | `Prefill=X, Decode=X` | 0 | 基线 |
| `S1` 只切后端 | `Prefill=qnn, Decode=gpu` | 1 | 最高 |
| `S2` 切后端 + 切 workpoint | `Prefill=qnn-hvx(1-6)-best, Decode=gpu-mid` | 1 | 很高 |
| `S3` 同后端不同 workpoint | `Prefill=qnn-hvx(1-6)-best-prefill, Decode=qnn-hvx(1-6)-best-decode` | 0 | 中 |
| `S4` CPU relaxed-SLO | `Prefill=qnn-hvx(1-6)-best, Decode=cpu-mid/low` | 1 | 中，主要面向 `SLO_factor=2-3` 的极端低功耗 |

### 4-C：当前最值得测的候选 policy

| Policy | 目标 | 当前依据 |
|--------|------|----------|
| `P1 = (Prefill=qnn-hvx(1-6)-best, Decode=gpu-high)` | strict-SLO phase-level 主候选 | 直接对应现有跨 phase Oracle 最强点 |
| `P2 = (Prefill=qnn-hvx<=6-opt, Decode=qnn-hvx<=6-opt)` | 同后端、不同 phase workpoint | 验证 QNN 内部 phase heterogeneity |
| `P3 = (Prefill=qnn-hvx(1-6)-best, Decode=gpu-mid)` | relaxed-SLO 降功耗 | 主要面向 `SLO_factor≈1.25-1.5` |
| `P4 = (Prefill=qnn-hvx(1-6)-best, Decode=cpu-mid/low)` | 极低功耗 decode 备选 | 主要面向 `SLO_factor≈2-3` |

### 4-D：剪枝原则

1. 若某策略同时慢于 `P1` 且能量也不占优，直接淘汰；
2. 若某策略只在极少数 workload 上占优，应将其收敛为 workload-specific policy，而不是全局默认；
3. 若某 backend 在某类请求长度下已明显不满足 SLO，则该 backend 不再进入该 workload bucket 的 workpoint 搜索；
4. 若 phase 切换开销已经吃掉 Oracle 预算，则该 workload bucket 不继续扩展 phase-level 动态策略。

| GPUOpenCL | low | 5.46 | 1.6300 | 5.46 | 1.5169 | 5.33 | 1.4426 | 需要 `SLO_factor≈5` 才能进入可行区，当前过慢 |

按 workload 归纳当前 `Decode` 侧 frontier：

1. `tg64 / tg256 / tg512` 三档下，**strict winner 都是 `gpu-high`**。
2. 若把 `SLO_factor` 放宽到约 `2.0`，**唯一稳定进入可行区的 workpoint 是 `gpu-mid`**：
   - `tg64`: slowdown `26.99 / 14.38 = 1.88`
   - `tg256`: slowdown `26.98 / 14.07 = 1.92`
   - `tg512`: slowdown `26.47 / 13.85 = 1.91`
3. `cpu1-mid` 与 `cpu1-low` 基本都卡在 `slowdown ≈ 2.04-2.08`，说明它们更接近：
   - `SLO_factor > 2.0` 才开始进入可行区
   - 但其总能量仍显著高于 `gpu-high / gpu-mid`
4. `gpu-low` 只有在 `SLO_factor≈5` 附近才有资格被考虑，因此不属于当前用户设定的 `rate=2/3` 主空间。
5. 因而，在**当前 decode 阶段**，真正值得保留到 policy map 的 relaxed-SLO 候选是：
   - `strict`: `gpu-high`
   - `rate≈2`: `gpu-mid`
   - `rate≈3`: 仍优先 `gpu-mid`；`cpu1-mid/low` 虽勉强可行，但从能量角度并不占优

这组结果对故事的直接含义是：

- 当前设备上的 decode power-tunable space **确实存在**，但主要体现在 **同一后端 GPU 的 high -> mid**，而不是“切到 CPU 就更省”；
- 这反过来说明，后续 phase-level 调度若要成立，decode 侧更像是在 `GPU workpoint selection` 上挖空间，而不是在 `GPU vs CPU` 之间大幅切换；
- 也说明当前 `SLO-aware scheduler` 的第一版 cost model 可以先把 decode 侧简化成：
  - `gpu-high`
  - `gpu-mid`
  - `cpu1-mid/low` 仅作为极端 fallback

### 5-E：2026-03-25 QNN Decode `hvx1-6` 功耗增量回填（当前最新 runtime）

> 本节的作用不是重写历史 `tg512` sweep，而是补齐更接近 request-level decode 的 `tg64 / tg256` 区间。  
> 重点问题是：`qnn-npu(full)` 在 decode 侧究竟是 strict-SLO 候选、near-strict 候选，还是只是历史参考。

| QNN workpoint | `tg64` | 功耗 (W) | 相对 `gpu-high` slowdown | `tg256` | 功耗 (W) | 相对 `gpu-high` slowdown | 当前判读 |
|---------------|-------:|---------:|-------------------------:|--------:|---------:|-------------------------:|----------|
| `hvx1` | 19.67 | 2.0906 | 1.37 | 20.53 | 2.7239 | 1.31 | 明显慢于 strict 基线，但仍显著快于 CPU |
| `hvx2` | 23.89 | 2.2952 | 1.13 | 24.51 | 2.8623 | 1.10 | 已进入 near-strict 区间，但平均功率不低于 GPU |
| `hvx3` | 24.52 | 2.2817 | 1.10 | 25.28 | 2.7557 | 1.07 | near-strict 候选；速度接近 GPU，功率也接近 |
| `hvx4` | 24.68 | 2.2900 | 1.09 | 25.40 | 2.7784 | 1.06 | 与 `hvx3/5/6` 基本收敛 |
| `hvx5` | 24.76 | 2.1209 | 1.09 | 25.57 | 2.7824 | 1.06 | 当前 decode 侧最值得保留的 QNN 点：near-strict 且平均功率略低 |
| `hvx6` | 24.69 | 2.1218 | 1.09 | 25.39 | 2.7926 | 1.06 | 与 `hvx5` 基本持平，无继续上调的明显必要 |

对 decode policy 的直接含义：

1. 相对于 `gpu-high`，`qnn hvx3-6` 在 `tg64 / tg256` 上都落在 `SLO_factor≈1.06-1.10` 区间，因此它们是**near-strict SLO 可行点**，不是 blocker。
2. 但如果目标是**总能量**，这些 `qnn` 点并没有赢过 `gpu-high`：
   - `tg64`: `gpu-high = 5.229 J`，`qnn hvx5 = 5.483 J`
   - `tg256`: `gpu-high = 26.730 J`，`qnn hvx5 = 27.857 J`
3. 如果目标是**平均功率**，`qnn hvx5 / hvx6` 仍然有价值：
   - `tg64`: `gpu-high = 2.2054 W`，`qnn hvx5 = 2.1209 W`
   - `tg256`: `gpu-high = 2.8169 W`，`qnn hvx5 = 2.7824 W`
4. 因而，当前 decode 侧可以分出两类 relaxed space：
   - `power-first near-strict`: `qnn hvx5 / hvx6`
   - `energy-first rate≈2`: `gpu-mid`
5. 这进一步强化了当前故事：  
   **decode 并不是简单的“GPU 永远最好”或“NPU 永远不适合”，而是存在一个由目标函数决定的 power-tunable space。**  
   只不过在当前设备和当前 runtime 下，这个空间主要体现为：
   - `strict / energy`: `gpu-high`
   - `near-strict / lower-power`: `qnn hvx5`
   - `rate≈2 / lower-power`: `gpu-mid`

## 6. 可直接复用的 Phase-Level Oracle

### 6-A：跨 Phase Oracle（`Prefill` + `Decode`）

> 现有 Oracle 结果主要覆盖 `pp128` 与 `pp512` 两档，因此它们更适合作为**中等 / 较大任务**的直接证据。  
> 对于本版 `PD` 主线，后续必须补齐 `pp16 -> pp2048` 的 phase-level Oracle，尤其是 `pp16 / pp32 / pp64` 这类小任务区间。

| Workload | 最优静态基线（时间 / 能量） | 跨 phase Oracle（时间 / 能量） | 相对最优静态延迟收益 | 相对最优静态能量收益 | 一次切换可容忍的额外时延预算 |
|----------|---------------------------:|-------------------------------:|--------------------:|--------------------:|----------------------------:|
| `pp128 + tg64` | `2.650 s / 7.120 J` | `2.569 s / 6.846 J` | `3.1%` | `3.8%` | `81 ms` |
| `pp128 + tg256` | `9.945 s / 26.875 J` | `9.863 s / 26.601 J` | `0.8%` | `1.0%` | `81 ms` |
| `pp512 + tg64` | `3.256 s / 8.263 J` | `2.963 s / 7.597 J` | `9.0%` | `8.1%` | `293 ms` |
| `pp512 + tg256` | `10.618 s / 28.526 J` | `10.258 s / 27.352 J` | `3.4%` | `4.1%` | `361 ms` |
| `pp512 + tg512` | `20.729 s / 55.907 J` | `20.368 s / 54.733 J` | `1.7%` | `2.1%` | `361 ms` |

### 6-B：当前最强的 phase-level 结论

1. 当前最明确、也最值得做的调度空间仍然是：  
   `Prefill = qnn-npu(full)`，`Decode = GPUOpenCL`
2. 与旧方案不同的是，本方案进一步要求在 phase-level 内纳入 **workpoint**：
   - `Prefill` 优先考虑 `qnn-hvx(1-6)` 中的最优点
   - `Decode` 优先考虑 `gpu-high`，其次评估 `qnn-hvx(1-6)` 与 `gpu-mid`
3. 但这只是当前已知数据下的**中大 workload 严格 `SLO_factor≈1` 候选**，不应直接外推为所有请求的默认策略。
4. 更高层的故事不是“某一条 phase 路由恒优”，而是：  
   **request-length heterogeneity + phase heterogeneity + per-phase power-tunable space**
5. 该结论当前还主要建立在 `pp128 / pp512` 这类 workload 上。  
   若要把它提升为系统级强结论，必须再回答：  
   **当 prompt 很短（`pp16-pp64`）时，phase 切换收益是否仍然存在，还是会被固定 overhead 吃掉。**

### 6-C：小任务 Phase-Level Oracle（`pp16 / pp32 / pp64`）

> 这里先给出**延迟优先**的 Oracle。  
> 对 `tg1`，直接使用第 `2-F` 节的 request-level 实测总时间：`Time = prompt_len / pp_tps + 1 / tg1_tps`。  
> 对 `tg16 / tg64`，使用 phase 分解近似：`Time = prompt_len / prefill_tps + gen_len / decode_tps`。  
> 当前小 prompt 的 `QNN prefill` 取 `hvx6` 作为 best-so-far；`QNN decode` 取 `hvx5` 作为当前 legal decode 代表点。

| Workload | 最优静态 / phase-level 候选 | 估计总时长 | 次优候选 | 差距 | 当前含义 |
|----------|----------------------------|----------:|----------|-----:|----------|
| `pp16 + tg1` | `CPU-2c static` | `0.122 s` | `GPU static` | `32.0%` | 超短回复的一次首 token 路径当前更偏向 `CPU-2c`，不应简单外推 GPU 恒优 |
| `pp32 + tg1` | `GPU static` | `0.166 s` | `CPU-2c static` | `29.5%` | 当 prompt 略增后，首 token winner 重新回到 `GPU` |
| `pp64 + tg1` | `GPU static` | `0.182 s` | `QNN static` | `36.3%` | `QNN` 即使 prefill 恢复，也不适合作为 `tg1` request-level winner |
| `pp16 + tg16` | `GPU/GPU` | `0.715 s` | `CPU-2c/GPU` | `4.1%` | 小任务下没有可见的跨 phase latency Oracle，最优就是全程 `GPU` |
| `pp32 + tg16` | `GPU/GPU` | `0.719 s` | `QNN(hvx6)/GPU` | `4.7%` | 即使允许跨 phase，`QNN prefill` 也没有反超 `GPU prefill` |
| `pp64 + tg16` | `GPU/GPU` | `0.735 s` | `QNN(hvx6)/GPU` | `2.6%` | 小任务 `tg16` 桶仍然没有 phase 分离收益 |
| `pp16 + tg64` | `GPU/GPU` | `2.483 s` | `CPU-2c/GPU` | `1.2%` | `tg64` 下第二名已经很接近，但最优仍是全程 `GPU` |
| `pp32 + tg64` | `GPU/GPU` | `2.486 s` | `QNN(hvx6)/GPU` | `1.4%` | 小任务进入 `tg64` 后，phase-level Oracle 仍未打开明显收益 |
| `pp64 + tg64` | `GPU/GPU` | `2.503 s` | `QNN(hvx6)/GPU` | `0.7%` | 到 `pp64 + tg64`，跨 phase latency slack 已经很薄，几乎不值得切换 |

当前直接结论：

1. 小任务并没有复现中大任务里的 `Prefill=qnn, Decode=gpu` 优势区。  
   对 `pp16 / pp32 / pp64`，strict latency Oracle 基本都退化成：
   - `tg1`: `CPU-2c` 或 `GPU` 静态路径
   - `tg16 / tg64`: `GPU/GPU`
2. 这说明**小任务区间的 phase heterogeneity 明显弱于中大任务**。  
   在 `pp16-pp64` 上，`QNN prefill` 虽然已经恢复可测，但还没有快到足以压过 `GPU prefill`。
3. 因而，小任务区间当前更像是：
   - `request-level backend selection` 问题
   - 而不是 `phase-level switching` 问题
4. 这组结果也解释了为什么后续真实 phase path 不应默认覆盖全部请求：  
   **如果连 latency-only Oracle 都没有分离，真实系统里的切换开销只会让情况更差。**

### 6-D：本节直接结论

如果 `Prefill -> Decode` 的一次 phase 切换开销低于上表预算，那么 phase-level policy 有机会同时优于单一静态后端。  
因此下一步最合理的实现目标不是继续切分 `Decode` 内部，而是尽快把真实的 phase-level path 做出来。

## 7. Phase-Level 实验设计

> 为了符合当前目标，本节应理解为三步法中的**第三步**：  
> 先做请求长度的 backend 适配性分析，再做 SLO-aware workpoint 放松，最后才验证 phase-level 动态路径。

### 7-0：三步实验流程

1. **Step-1：Request-length backend affinity**  
   在不同 `prompt_len / gen_len` 组合上，建立 `Prefill` 与 `Decode` 各自的 backend 优势区间。
2. **Step-2：SLO-aware workpoint relaxation**  
   对每个 backend 优势区间，测试在不同 `SLO_factor` 下能否把 CPU/GPU/QNN 工作点下调而仍满足约束。
3. **Step-3：Phase-level dynamic validation**  
   只在 `Prefill` 与 `Decode` 的后端偏好分离、且静态 workpoint 调整仍不够时，再验证动态切换是否值得。

### 7-A：真实 phase-level 路径验证

#### 目标

- 把 `Prefill=qnn, Decode=gpu` 从 Oracle 变成真实系统路径；
- 量化真实 phase 切换开销；
- 验证真实收益与 Oracle 的差距；
- 判断它在整个 `request-length × SLO_factor` 空间中究竟覆盖哪些区域，而不是默认覆盖全部请求。

#### 最小实验矩阵

| 类别 | `Prefill` | `Decode` | 主要 workload | 目的 |
|------|-----------|----------|---------------|------|
| P1-strict | `qnn-hvx(1-6)-best-prefill` | `gpu-high` | `pp16/32/64 + tg1/16/32/64`，`pp128/256/512 + tg64/256`，`pp1024/2048 + tg256/512` | 验证最强 phase-level 主候选在全区间是否成立 |
| P2-balanced | `qnn-hvx(1-6)-best-prefill` | `qnn-hvx(1-6)-best-decode` | 同上 | 验证“全程 QNN，但 phase 内部 workpoint 不同” |
| P3-relaxed | `qnn-hvx(1-6)-best-prefill` | `gpu-mid` | 重点看 `pp16-pp256 + tg16-128`，并补 `pp512/1024` | 验证 relaxed-SLO 下的 GPU 降功耗空间 |
| P4-cpu-relaxed | `qnn-hvx(1-6)-best-prefill` | `cpu1-mid/low` | 重点看 `pp16-pp128 + tg16/32/64` | 验证小任务 / 宽松 SLO 下的极低功耗 decode 备选 |

#### workload 分层要求

- 小任务必须作为一等公民单独汇报，不能被并入中大任务平均值；
- 至少要覆盖 `pp16 / pp32 / pp64 / pp128 / pp256 / pp512 / pp1024 / pp2048` 八档 prompt；
- 对每档 prompt，优先测 `tg1 / tg16 / tg64`，再按资源情况补 `tg256 / tg512`；
- 汇报 phase-level policy 时，必须明确它适用的是哪一段 workload，而不是默认一套策略覆盖全部请求。

#### 需要输出

- 请求长度到 backend 适配性的静态映射
- `SLO_factor -> 可接受 workpoint` 的前沿边界
- 端到端 wall-time / tok/s
- 平均功耗与总能量
- `Prefill -> Decode` 一次切换的额外时延
- 与第 `6-A` 节 Oracle 的差距

### 7-B：Phase-Level Cost Model

对任意请求，统一定义：

```text
Req = (prompt_len, gen_len, SLO_factor)
Policy = (prefill_backend, prefill_wp, decode_backend, decode_wp)
```

代价模型的输入至少包括：

- `prompt_len`
- `gen_len`
- `SLO_factor`
- phase-level 的静态 `tok/s`
- phase-level 的平均功耗
- 一次 `Prefill -> Decode` 切换开销

并且需要补充两条约束：

1. 代价模型必须在 `prompt_len ∈ [16, 2048]` 上拟合，而不是只用 `pp128 / pp512` 推断全部请求；
2. 小任务（尤其 `pp16-pp64`）应单独建模或至少单独分 bucket，因为固定切换开销在该区间不再可忽略。
3. `qnn` workpoint 的合法候选集应由设备真实可用 `n_hvx_threads` 上限决定；若上限为 `6`，则只允许 `1-6` 进入 cost model 的正式搜索空间。

代价模型的输出：

- 推荐 backend bucket
- 推荐 workpoint bucket
- 是否满足 `SLO_factor`
- 预测总时间
- 预测总能量
- 推荐 policy（静态或 phase-level）

#### 7-B.1：`SLO_factor` 的判定方式

对于 workload `w`，先从已测 config 中得到：

```text
Perf_best(w) = max_P Perf(P, w)
```

然后对任意候选 `P` 定义：

```text
slowdown(P, w) = Perf_best(w) / Perf(P, w)
```

当且仅当：

```text
slowdown(P, w) <= SLO_factor
```

时，认为该 config 满足该 workload 的 SLO。

因此文档里的“能否降频”本质上是在问：

- 对于给定 workload 与 backend，
- 是否存在更低功耗 workpoint `wp'`，
- 使得 `slowdown(P_wp', w) <= SLO_factor`，
- 同时总能量或平均功耗优于更高 workpoint。

#### 7-B.2：建议的 `SLO_factor` 扫描点

为减少实验矩阵膨胀，当前建议统一扫描以下六档：

- `1.0`
- `1.1`
- `1.25`
- `1.5`
- `2.0`
- `3.0`

其作用分别是：

- `1.0 / 1.1`：判断最优 config 附近是否已经存在低功耗替代点；
- `1.25 / 1.5`：判断 GPU 中频、QNN 较低并发等 workpoint 是否开始进入可行区；
- `2.0 / 3.0`：判断 CPU mid/low、GPU low 或更激进的 QNN 降并发是否进入可行区。

### 7-C：切换开销测量

本方案中必须单独测量的 overhead 只有一个：

- `Prefill -> Decode` 边界切换开销

> **2026-03-26 补充**：这里的 `KV migration` 不能再被写成一个统一常数。  
> 对本项目来说，它至少是一个：
>
> ```text
> KV_migration_cost = f(producer_backend, consumer_backend, storage_backend, transfer_mode, zero_copy, payload_size)
> ```
>
> 也就是说：
>
> - `CPU -> QNN`
> - `QNN -> OpenCL`
> - `OpenCL -> CPU`
> - `QNN -> CPU`
> - `CPU -> OpenCL`
> - `OpenCL -> QNN`
>
> 这些都不应被默认看成“同一种 migration”。

建议拆成三部分：

1. `T_switch_runtime`
   - backend rebind
   - context / graph setup
2. `T_switch_memory`
   - activation / KV / residual 边界处理
3. `T_switch_idle_overlap`
   - 切换期间多 runtime 同时活跃导致的额外功耗

#### 7-C.0：backend pair 视角下的 KV migration 约束

当前文档后续凡是提到 `KV migration / T_switch_memory`，都必须默认附带 backend pair 语义，而不是把它当作单一常数。

从当前实现看，至少要区分以下几类边界：

| producer -> consumer | 当前典型 contract / storage | 当前关注点 |
|----------------------|-----------------------------|------------|
| `CPU -> OpenCL` | `CPU_OPENCL_ZERO_COPY`, `opencl-host` | 更接近 host-visible / shared-buffer 的 zero-copy 问题 |
| `OpenCL -> CPU` | `CPU_OPENCL_ZERO_COPY` 或 fallback | 不一定等价于 `CPU -> OpenCL`，读回 correctness / coherence 更关键 |
| `QNN -> OpenCL` | `QNN_RPCMEM`, `qnn-npu-host` 或 consumer-owned legacy | 当前主线最关键 pair |
| `OpenCL -> QNN` | `QNN_RPCMEM`, `qnn-npu-host` 或 fallback | 若后续考虑 `Prefill=gpu, Decode=qnn`，不能直接套用 `QNN -> OpenCL` 的结论 |
| `QNN -> CPU` | `QNN_RPCMEM`, `qnn-npu-host` 或 fallback | host materialization 与 CPU 消费代价 |
| `CPU -> QNN` | `QNN_RPCMEM`, `qnn-npu-host` 或 fallback | staging / upload 问题，不能默认等同于 `QNN -> CPU` |
| same-backend controls | `CPU -> CPU`、`OpenCL -> OpenCL`、`QNN -> QNN` | 检查哪些路径本不该发生 migration |

当前直接要求：

1. 后续任何 `KV migration` 结果都必须写明 backend pair。
2. 不允许把 `QNN -> OpenCL` 的测量值直接泛化成 `CPU -> QNN` 或 `OpenCL -> CPU` 的代表值。
3. same-backend control 必须保留，因为它能验证：
   - 当前 runtime 是否错误地在“无边界切换”情况下仍支付 migration
   - 某笔成本到底属于 route skeleton，还是属于真实跨 backend KV contract

#### 7-C.1：当前优先测量矩阵

考虑当前主线和实现优先级，当前最该补齐的不是“三个后端所有组合平均一下”，而是按以下顺序推进：

1. `QNN -> OpenCL`
   - 当前 phase-level 主线最关键 pair
   - 需要补 prompt 长度 sweep，重点看 `kv_migration_us` 随 `pp32 / 64 / 128 / 512` 如何变化
2. `QNN -> CPU`
   - 用来判断 relaxed SLO 下 `Decode=CPU` 是否存在更低的切换成本
3. `CPU -> OpenCL` 与 `OpenCL -> CPU`
   - 作为 host-visible / zero-copy 边界的对照组
4. `CPU -> QNN` 与 `OpenCL -> QNN`
   - 当前不是最高优先级，但若后续探索 `Prefill=gpu/cpu, Decode=qnn`，则必须补

#### 7-C.2：测完以后，必须继续尝试减少 overhead

当前主线不应停在“把 migration 测出来”。  
在 backend pair 矩阵测完后，下一步应明确转向：

- **针对最贵、最常见的 backend pair 去主动降低 overhead**

当前文档应把后续优化目标写清楚：

1. 优先降低 `QNN -> OpenCL` 的 `KV migration`
   - 因为这是当前 phase-level 主线里最关键、也最可能真正使用的边界
2. 若 `QNN -> CPU` 在 relaxed SLO 区域出现潜在收益，也应优先降低其 migration 成本
3. `CPU <-> OpenCL` 更适合作为“shared-buffer / zero-copy 是否真的成立”的对照组；若这里已经很低，就不应优先投入过多工程复杂度

这里的“减少 overhead”至少应包括：

- 减少 route switch 本身的控制流成本
- 减少 KV payload staging / row assembly
- 减少真正写入 consumer-visible KV tensor 的 flush 成本
- 优化 storage backend / buffer residency 的选择
- 若可能，继续降低 decode-entry bootstrap 与 steady-state orchestration 的残余成本

| `tracev5c` | `pp128 + tg256` | 修复后复测 | `24.20 tok/s` | `4.2202 W` | `decode_count = 256`；首 token `total_wall_us = 132693`，其中 `reserve_us = 30172`、`bootstrap_sync_us = 39814`；后续 `255` 个 token 全部为 `already-active`，steady-state `reserve_us_sum = 0`，`graph_runs_reused = 254`，steady-state `total_wall_us ≈ 40.90 ms/token` | 长 decode 下也已确认：当前不再存在每 token 的 `decode/base` 来回切换 |

当前可下的强结论：

1. **切换开销已经被真实量化**，而且现在是**框架内分项量化**，不是仅靠端到端差值猜测。
2. **主要 bug 已经修复并显著降低了 runtime overhead**：  
   `pp128 + tg64` 的 decode 吞吐从 `14.00 tok/s` 提升到 `22.02 tok/s`；`pp128 + tg256` 在修复后也能稳定到 `24.20 tok/s`。
3. 当前剩余 gap 已经不再是“每个 token 都在重复 route 切换”，而更集中在两处：
   - 首个 decode token 的 bootstrap / sync / 首次 rebuild
   - steady-state 中仍高于纯静态 `GPUOpenCL` 的残余 runtime 开销
4. 若以当前文档中的静态 `GPUOpenCL` decode 基线 `~26.3 tok/s` 作为参照，则修复后：
   - `pp128 + tg64` 还差约 `16.3%`
   - `pp128 + tg256` 还差约 `8.0%`
   这说明 phase-level 路径已经明显更接近可用区，但还不能宣称“真实系统已完全兑现 Oracle”。
5. 更重要的是，当前证据把瓶颈形态收窄了：  
   **剩下要追的不是 per-token route thrash，而是 decode-entry bootstrap 与 steady-state orchestration 的残余成本。**

8. `Roofline / bound diagnosis` 继续挂起，等第 7 项中的剩余 gap 被拆清后再启动。

### 9-C：成功 / 失败分别意味着什么

- **若 backend affinity map 清晰且 workpoint slack 明显**：说明当前最主要的系统空间是“按请求长度选 backend，再按 `SLO_factor` 选 workpoint”
- **若只有 workpoint slack 成立，而 phase-level 动态路径失败**：说明系统仍有实用价值，但主线应更偏向 `SLO-aware DVFS / workpoint control`，而不是动态切换
- **若 phase-level 路径也成功**：说明在部分 request bucket 上，`Prefill / Decode` 的 phase-level 调度可以进一步优于静态方案
- **若 phase-level 路径失败**：说明当前 runtime 下，连一次 phase 切换都已过重，研究重点应转回 runtime / switch overhead 本身
