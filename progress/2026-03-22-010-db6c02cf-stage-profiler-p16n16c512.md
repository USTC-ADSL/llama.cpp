# 任务 010：补齐主设备 `db6c02cf` 的最小分阶段 profiling 结果

日期：2026-03-22

## 背景与目标

在主设备的：

- static baseline
- decode mixed-route 验证
- prefill full-vs-split 对照

都已经具备之后，下一项最高优先级非功耗任务是：

- `P3-1 Decode 分阶段 profiling`

如果没有一组最小可用的 `phase × stage × backend` 数据，后续就很难回答：

- static `qnn-npu` 到底是被哪个阶段拖慢；
- `Prefill/Decode` 的阶段异构性是不是已经能从真实测量里看到；
- 哪些阶段值得继续进入 `P4-1/P4-2` 的 overhead 分解。

这项任务的最小目标是：

1. 用同一组轻量参数拿到 `CPU` 与 `qnn-npu` 的分阶段 JSON。
2. 明确 `GPUOpenCL` 当前为什么还没法进入同一张表。
3. 把结果归档到 `progress/` 和 `docs/`，供主线后续直接复用。

## 执行内容

### 1. 重新按规范构建 profiling 版本

执行：

- `./build-npu-opencl.sh build-qnn-prof-db arm64-android-snapdragon-release --without-npu --with-gpu --with-qnn --with-profiling`

构建成功后，将 `build-qnn-prof-db/bin` 部署到：

- `/data/local/tmp/acom-stage-profiler-qwen2`

### 2. 确认设备处于唤醒态

执行了：

- `adb -s db6c02cf shell input keyevent KEYCODE_WAKEUP`
- `adb -s db6c02cf shell input keyevent KEYCODE_POWER`
- `adb -s db6c02cf shell wm dismiss-keyguard`

并确认：

- `mWakefulness=Awake`
- `mHoldingDisplaySuspendBlocker=true`

### 3. 使用同尺度参数补 `CPU` 与 `qnn-npu`

统一参数：

- `-p 16`
- `-n 16`
- `-c 512`
- `-t 1`
- `--ignore-eos`

CPU：

- `LD_LIBRARY_PATH=. ./llama-stage-profiler ... -ngl 0 -fit off`

QNN：

- `GGML_HEXAGON_EXPERIMENTAL=1 ADSP_LIBRARY_PATH=. LD_LIBRARY_PATH=. ./llama-stage-profiler ... -ngl 99 -dev qnn-npu -fit off`

结果都成功写出 JSON，虽然进程在 teardown 阶段仍以 `134` 退出。

### 4. 尝试补 `GPUOpenCL`

尝试了两组更保守配置：

1. `p16 / n16 / c512 / -fit off`
2. `p8 / n8 / c256 / -fit on`

两者都在模型加载阶段失败，没有写出 JSON。

## 关键证据

### 1. `CPU / qnn-npu` 的同尺度分阶段 JSON 已经落盘

本地归档：

- `tmp/db6c02cf_cpu_decode_stage_p16_n16_c512_20260322.json`
- `tmp/db6c02cf_cpu_decode_stage_p16_n16_c512_20260322.log`
- `tmp/db6c02cf_qnn_decode_stage_p16_n16_c512_env_20260322.json`
- `tmp/db6c02cf_qnn_decode_stage_p16_n16_c512_env_20260322.log`

整理后的 CSV：

- `docs/qnn-attn-core-shared/db6c02cf-stage-profiler-p16n16c512-2026-03-22.csv`

分析文档：

- `docs/qnn-attn-core-shared/db6c02cf-stage-profiler-p16n16c512-2026-03-22.md`

### 2. `Decode` 里 `qnn-npu` 主要输在 `Attn_Core` 与 `FFN`

同配置下的 `Decode mean_us`：

| Stage | CPU | qnn-npu | qnn/CPU |
|------|----:|--------:|--------:|
| `Attn_Proj` | `906.19` | `871.39` | `0.96x` |
| `KV_Cache` | `1631.12` | `1736.14` | `1.06x` |
| `Attn_Core` | `111.68` | `579.72` | `5.19x` |
| `FFN_Block` | `864.21` | `1234.62` | `1.43x` |

这说明 static `qnn-npu` decode 差，不是因为所有阶段都差，而是：

- `Attn_Core`
- `FFN_Block`

这两个关键阶段当前明显不占优。

### 3. `Prefill` 已经出现清晰的阶段异构

同配置下的 `Prefill mean_us`：

| Stage | CPU | qnn-npu | qnn/CPU |
|------|----:|--------:|--------:|
| `Attn_Proj` | `194.84` | `180.11` | `0.92x` |
| `KV_Cache` | `124.09` | `274.23` | `2.21x` |
| `Attn_Core` | `312.42` | `4017.45` | `12.86x` |
| `FFN_Block` | `5843.39` | `1990.58` | `0.34x` |

端到端 `Prefill` 总时间却几乎一样：

- `CPU = 155.39 ms`
- `qnn-npu = 155.10 ms`

这说明：

- `FFN` 在 `qnn-npu` 上确实更像强项；
- 但 `Attn_Core` 与 `KV_Cache` 会把这部分收益吃回去。

### 4. `GPUOpenCL` blocker 已经收敛为内存分配问题

本地日志：

- `tmp/db6c02cf_gpu_decode_stage_p16_n16_c512_20260322.log`
- `tmp/db6c02cf_gpu_decode_stage_p8_n8_c256_20260322.log`

两条日志都收敛到同一类错误：

- `llama_model_load: error loading model: unable to allocate OpenCL buffer`

因此当前不能把 `GPUOpenCL` 的缺失模糊写成“没时间测”或“偶发失败”，更准确的表述是：

- **stage-profiler 路径下的 OpenCL model-load 内存分配当前是正式 blocker**

## 当前结论

这项任务完成后，可以形成四条直接可用的结论：

1. `P3-1` 已经从“完全没有分阶段数据”推进到“有一组同尺度 `CPU / qnn-npu` `Decode` 数据可用”。
2. `P3-2` 也获得了一组最小 `Prefill` 数据，因为同一条 JSON 同时包含了 `Prefill` 阶段信息。
3. 当前主设备 static `qnn-npu` 的阶段特征已经比较清楚：
   - `Decode`：`Attn_Core` 和 `FFN` 是主要短板；
   - `Prefill`：`FFN` 是潜在优势阶段，但 `Attn_Core` 与 `KV_Cache` 明显拖后腿。
4. `GPUOpenCL` 的 stage-profiler 缺口现在已有明确 blocker，可以作为后续主线待解决问题记录，而不是继续停留在“不知道为什么没跑出来”。

## 下一步

1. 在主线工作计划中把 `P3-1/P3-2` 更新为“部分完成/进行中”。
2. 先用这组 `CPU / qnn-npu` 数据推进：
   - `P4-1 Decode 边界 overhead 分解`
3. 后续再决定是：
   - 继续攻 `GPUOpenCL` 的 stage-profiler 内存问题；
   - 还是改用更贴近端到端路径的内嵌 profiler 来补 GPU 这一列。
