## 目标

补一组第二台设备上的最小 decode baseline，用于后续和主设备做 cross-device 对照。

本轮只尝试：

- `CPU` 单线程 decode
- `GPUOpenCL` decode
- `qnn-npu` decode

统一设置：

- 工具：`llama-bench`
- 模型：`qwen2_0.5b`
- `-p 0 -n 128 -c 2048 -b 1 -ub 1`
- `-ctk f16 -ctv f16`
- `-t 1`
- `--no-warmup`

补跑 `qnn-npu` static baseline 时额外使用：

- `-r 1`

为绕过 Android/QNN 退出阶段的 runtime finalizer 崩溃，本轮补跑 `CPU` / `qnn-npu` baseline 时额外使用：

- `LLAMA_BENCH_FAST_EXIT=1`

## 亮屏状态

这部分目前还不能作为严格的“亮屏基线”使用。

原因：

- 直接记录的 `dumpsys power` 日志里，before/after 都仍然是 `mWakefulness=Asleep`
- 我尝试过：
  - `svc power stayon true`
  - `am start -a android.settings.SETTINGS`
- 单独执行唤醒命令后，设备短暂返回过 `mWakefulness=Awake`
- 但把 baseline 命令串起来后，记录下来的 power state 仍然回到了 `Asleep`

因此，本文件中的结果应视为：

- **第二台设备的 preliminary baseline**
- **不是严格满足亮屏条件的正式基线**

## 失败项说明

### 1. `qnn-npu` static baseline 已从 reserve-abort 推进到可测

旧问题的报错核心信息是：

`pre-allocated tensor (cache_k_upd-0) in a buffer (qnn-npu) that cannot run the operation (SET_ROWS)`

当前 tree 下已经通过把 static `qnn-npu` 的 KV cache 放到 `qnn-npu-host`，消除了这条 scheduler reserve 阶段的硬崩溃。

verbose 日志里的关键证据：

- `llama_kv_cache: static qnn-npu KV cache uses qnn-npu-host so cache SET_ROWS/GET_ROWS can stay on a host-visible buffer while preserving qnn-npu decode offload`
- 24 层 KV cache 全部显示为 `dev = qnn-npu-host`
- `llama_kv_cache: qnn-npu-host KV buffer size = 24.00 MiB`
- `llama-bench` 已能打印：`tg128 = 10.83 ± 0.00`

这说明静态单后端 `qnn-npu` decode 已经不再卡死在 `SET_ROWS/cache_k_upd-0` 的 buffer placement 冲突上。

但这条 baseline 仍然不是“正式完成”的状态，因为：

- 当前 tok/s 很可能已经受到 host-visible KV placement 的 runtime overhead 影响
- 即使现在可以通过 `LLAMA_BENCH_FAST_EXIT=1` 让 bench 干净退出，底层 QNN teardown bug 仍未根治
- 因此它更适合作为 **可采集的 static qnn-npu baseline**，而不是理想单后端 NPU 上界

### 2. `llama-context` 去重补丁清掉了重复 `qnn-npu` free，但没有清掉底层 crash

在 `src/llama-context.cpp` 中跳过重复 ACCEL backend 初始化之后，`qnn-npu` verbose 日志的析构尾部已经从：

- `idx 0, name:qnn-cpu`
- `idx 2, name:qnn-npu`
- `idx 2, name:qnn-npu`

变成：

- `idx 0, name:qnn-cpu`
- `idx 2, name:qnn-npu`

对应日志：

- `tmp/fd8657d6_qnn_npu_decode_tg1_verbose_after_ctxdedup.log`

这说明“重复注册 / 重复释放 `qnn-npu` backend”那条症状已经被修掉。

但是进程仍然在退出阶段 `Aborted`，所以根因不再是简单的 duplicate backend free。

### 3. 真正的 exit-time abort 根因在 `libQnnHtpPrepare.so` finalizer

设备 crash buffer 的关键信息见：

- `tmp/fd8657d6_crash_logcat_after_ctxdedup.log`

其中同时记录到了两条命令的崩溃：

- `qnn-npu`: `./llama-bench -r 1 ... -ngl 99 -dev qnn-npu ...`
- `CPU`: `./llama-bench -r 1 ... -ngl 0 ...`

两者的共同特征是：

- `Abort message: 'Scudo ERROR: corrupted chunk header ...'`
- backtrace 落在 `/data/local/tmp/acom-baseline/libQnnHtpPrepare.so`
- 栈尾位于 `__cxa_finalize -> exit`

这说明当前 `fd8657d6` 上的退出阶段 abort 更像是 Android/QNN 运行时库 finalizer 的 heap corruption，而不是 decode 计算本身没有跑完。

### 4. 当前 bench 采集路径可通过 `LLAMA_BENCH_FAST_EXIT=1` 跑通

为避免“结果已经打印出来，但最后因为 QNN runtime finalizer abort 导致脚本失败”，当前 tree 下给 `tools/llama-bench/llama-bench.cpp` 增加了一个显式开关：

- `LLAMA_BENCH_FAST_EXIT=1`

行为是：

- 在结果表和 build 信息已经打印并 flush 之后，直接 fast-exit
- 跳过 `llama_backend_free()` 以及后续 Android/QNN 共享库 finalizer

这不是对底层 `libQnnHtpPrepare.so` heap corruption 的根因修复，而是一个 **bench-only workaround**，用于保证静态 baseline 可以稳定采集。

对应成功日志：

- `tmp/fd8657d6_qnn_npu_decode_tg128_r1_fast_exit.log`
- `tmp/fd8657d6_cpu_decode_tg128_fast_exit.log`

### 5. `attn_core` AoT 产物已补齐，但第二台设备的 AoT decode 仍不稳定

这轮已经确认并补推了两组缺失的 AoT 产物：

- `qnn_attn_core_batch1`
- `qnn_attn_core_batch128`

因此旧的缺文件报错：

- `failed to mmap ... attn_core_layer_0.bin, errno=2`

不再是当前 blocker。

但在我本地复现的最新 AoT decode 中，这条路径依然不能稳定跑到有效 stage 执行：

- 不带显式 route：
  - `tmp/fd8657d6_qnn_aot_decode_reserve_abort_after_artifacts.log`
  - scheduler reserve abort：
    - `pre-allocated tensor (blk.0.attn_norm.weight) in a buffer (qnn-npu) that cannot run the operation (NONE)`
- 带显式 stage route：
  - `tmp/fd8657d6_qnn_aot_decode_with_route_reserve_abort_after_artifacts.log`
  - scheduler reserve abort：
    - `pre-allocated tensor (output_norm.weight) in a buffer (qnn-npu) that cannot run the operation (NONE)`

所以第二台设备目前可以给出的判断应分成两层：

- **static `qnn-npu` baseline 已经可测，`tg128 = 10.83 tok/s`**
- **AoT decode 的缺文件问题已解除，但这条路径仍然会在更早的 reserve / param placement 阶段 abort，暂时不能作为稳定 AoT 基线**

## 当前可用的最小结论

在 `fd8657d6` 上，当前已经拿到三条 decode 路径的最小可用 tok/s 观测值：

- `CPU tg128 = 14.67 tok/s`
- `GPUOpenCL tg128 = 74.33 tok/s`
- `qnn-npu tg128 = 10.83 tok/s`

其中最重要的新增进展是：

- static `qnn-npu` baseline 已经不再在 scheduler reserve 阶段直接失败
- `llama-context` 去重补丁已经清掉了重复 `qnn-npu` free 这条症状
- 通过 `LLAMA_BENCH_FAST_EXIT=1`，第二台设备上的 `CPU` / static `qnn-npu` decode baseline 现在都可以作为 `llama-bench` 采集路径跑通
- 缺失的 `attn_core` AoT 产物已经补到设备上，但 AoT decode 仍然停在 reserve / param placement abort，而不是进入稳定的 stage 执行

但如果要把第二台设备纳入正式对照实验，仍然需要先解决三个问题：

1. 亮屏状态需要能稳定保持并且可被日志确认。
2. `libQnnHtpPrepare.so` 在 `__cxa_finalize` 阶段的 heap corruption 仍需要真正定位；当前 `LLAMA_BENCH_FAST_EXIT=1` 只是 bench 采集 workaround。
3. AoT decode 还需要一个稳定的 reserve / graph-placement 路径，否则第二台设备只能提供 static baseline，不能提供可解释的 AoT stage 数据。
