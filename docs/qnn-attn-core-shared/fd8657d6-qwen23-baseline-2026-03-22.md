# `fd8657d6` 上的 `Qwen2/Qwen3` 非功耗基线与 QNN AoT 复核

更新日期：2026-03-22

## 目标

这轮实验的目标不是测功耗，也不是直接证明动态调度收益，而是先在第二台设备 `fd8657d6` 上补齐两类模型的最小可用性能基线，并把 `qnn-npu` static route 与 `QNN AoT full-graph` route 严格区分开：

- `Qwen2-0.5B`
- `Qwen3-1.7B-Q8_0`

覆盖两条主线：

- `Decode` static baseline
- `Prefill` static baseline
- `QNN AoT full-graph` 复核

并给后续：

- `phase × stage × backend` 矩阵
- runtime overhead 分解
- 功率与 `SLO-aware` 调度

提供第二设备对照。

## 亮屏与 root 状态

本轮结果不能视为“严格亮屏、严格功耗可比”的正式基线。

原因有两点：

1. `fd8657d6` 当前 `shell` 环境下没有 `su`：
   - `adb shell su -c id` 直接返回 `su: inaccessible or not found`
   - 因此我无法把它当作“可直接 root 控制”的设备来使用
2. 亮屏控制只有部分成功：
   - `svc power stayon true` 后，许多命令开始前都能看到：
     - `mWakefulness=Awake`
     - `mHoldingDisplaySuspendBlocker=true`
   - 但 `settings get global stay_on_while_plugged_in` 仍然是 `0`
   - 说明这轮更准确的表述应当是：
     - **运行开始时设备处于唤醒态**
     - **但亮屏状态仍不够可控，不能拿来做正式功耗实验**

因此本轮只记录性能，不采功耗。

## Decode baseline

CSV：

- `docs/qnn-attn-core-shared/fd8657d6-qwen23-decode-baseline-2026-03-22.csv`

### `Qwen2-0.5B`

| 后端 | `tg1` | `tg128` |
| --- | ---: | ---: |
| CPU | `14.74` | `14.76` |
| GPUOpenCL | `74.32` | `74.70` |
| qnn-npu | `10.87` | `10.92` |

### `Qwen3-1.7B-Q8_0`

| 后端 | `tg1` | `tg64` |
| --- | ---: | ---: |
| CPU | `16.02` | `15.84` |
| GPUOpenCL | `27.11` | `27.17` |
| qnn-npu | `10.12` | `10.07` |

直接观察：

- 两个模型在 `Decode` 上的静态最强后端都是 `GPUOpenCL`
- `qnn-npu` 在两个模型上都接近或低于 CPU
- `Qwen3-1.7B` 上 GPU 仍然最强，但领先幅度比 `Qwen2-0.5B` 明显缩小：
  - `Qwen2`: `74.32 / 14.74 / 10.87`
  - `Qwen3`: `27.11 / 16.02 / 10.12`

这说明：

- 第二设备上同样存在明确的后端差异；
- 但更大模型并没有自动把 `qnn-npu` 推成静态 decode 最优；
- `Decode` 侧仍然不应把 “static NPU 最强” 当作前提。

## Prefill baseline

这一节的 `qnn-npu` 数字必须特别说明：

- 它们对应的是 **static non-AoT `qnn-npu`** 路线；
- 命令里没有使用 `GGML_QNN_AOT_CONFIG`；
- 因此这些数字不能被当成“QNN full-graph AoT 吞吐”。

CSV：

- `docs/qnn-attn-core-shared/fd8657d6-qwen23-prefill-baseline-2026-03-22.csv`

### `Qwen2-0.5B`

| 后端 | `pp128` | `pp256` | `pp512` |
| --- | ---: | ---: | ---: |
| CPU | `325.29` | `329.79` | `267.00` |
| GPUOpenCL | `1360.94` | `1773.88` | `1343.09` |
| qnn-npu | `323.28` | `325.31` | `260.76` |

### `Qwen3-1.7B-Q8_0`

| 后端 | `pp64` | `pp128` | `pp256` |
| --- | ---: | ---: | ---: |
| CPU | `86.75` | `89.07` | `65.95` |
| GPUOpenCL | `383.59` | `530.85` | `582.85` |
| qnn-npu | `75.28` | `66.02` | `65.93` |

直接观察：

- 两个模型在 `Prefill` 上的静态最强后端仍然都是 `GPUOpenCL`
- `Qwen2-0.5B` 上，`qnn-npu` 和 CPU 基本重合
- `Qwen3-1.7B-Q8_0` 上，`qnn-npu` 明显低于 CPU，也远低于 GPU

因此第二设备上的这组 **static non-AoT** `Prefill` 结论与主设备方向一致：

- 静态 `GPUOpenCL` 最强
- 静态 `qnn-npu` 不占优
- 后续若要讨论 `Prefill` 异构收益，仍必须把 runtime overhead 当成核心变量，而不是假设 NPU 天然最好

## `Qwen2` QNN AoT full-graph 复核

用户指出：

- `Qwen2` 在 QNN AoT full-graph 下的速度本应接近 `2000 tok/s` 甚至更高；
- 先前这组 `~323 tok/s` 的 `qnn-npu` 结果明显不对。

复核后确认，问题不在“QNN full-graph 本身很慢”，而在于：

- 之前跑到的是 **static non-AoT `qnn-npu`**；
- 不是带 `GGML_QNN_AOT_CONFIG` 的 full-graph AoT 实验。

本次复核使用：

- `GGML_QNN_AOT_CONFIG=/data/local/tmp/acom-attn-proj-verify/models/qwen2_0.5b/qnn/config.json`
- `GGML_QNN_AOT_MODEL_DIR=/data/local/tmp/acom-attn-proj-verify/models/qwen2_0.5b/qnn`
- 模型：
  - `/data/local/tmp/acom-attn-proj-verify/models/qwen2_0.5b/ggml/weights.gguf`
- 设备：
  - `taskset 80 -t 1 -ngl 99 -dev qnn-npu --mmap 0`
- 仍保留：
  - `GGML_HEXAGON_EXPERIMENTAL=1`
  - `LLAMA_BENCH_FAST_EXIT=1`

CSV：

- `docs/qnn-attn-core-shared/fd8657d6-qwen2-aot-fullgraph-prefill-2026-03-22.csv`

结果：

| 模式 | `pp128` | `pp256` |
| --- | ---: | ---: |
| static non-AoT `qnn-npu` | `323.28` | `325.31` |
| QNN AoT full-graph | `4280.48` | `4565.30` |

对应日志：

- `tmp/fd8657d6_qwen2_qnn_aot_fullgraph_prefill_pp128_20260322.log`
- `tmp/fd8657d6_qwen2_qnn_aot_fullgraph_prefill_pp256_20260322.log`

因此这里可以形成一个强结论：

- 先前 `~323 tok/s` 的结果不是 `Qwen2` full-graph AoT 性能；
- `fd8657d6` 上 `Qwen2` full-graph AoT prefill 的真实量级是 `4k tok/s`；
- 用户对“这组数不应该这么慢”的判断是对的，问题来自实验类别混淆，而不是 full-graph AoT 本身退化到 static `qnn-npu` 水平。

## `Qwen3` QNN AoT full-graph 状态

这轮没有在 `fd8657d6` 上复核出 `Qwen3` full-graph AoT 吞吐，原因不是 bench 命令本身失败，而是当前设备上缺少对应 AoT 产物。

设备侧实际可见的是：

- `Qwen2` AoT 目录下有：
  - `config.json`
  - `qwen2_0.5b_0.bin`
  - `lm_head.bin`
- 但当前没有发现 `Qwen3` 对应的：
  - full-graph `config.json`
  - `lm_head.bin`
  - 配套 graph `.bin`

因此当前对 `Qwen3` 更准确的表述应是：

- `fd8657d6` 上已经有 `Qwen3` 的 static `CPU / GPUOpenCL / qnn-npu` baseline；
- 但还没有可复现的 `Qwen3` full-graph AoT 复核条件；
- 所以不能把当前 `66 tok/s` 的 static `qnn-npu pp128` 误写成 “`Qwen3` full-graph AoT 很慢”。

## 需要特别标记的风险

### 1. `Qwen3 qnn-npu prefill` 对运行状态较敏感

在正式批量跑之前，`Qwen3 qnn-npu pp64` 的 smoke 结果是：

- `89.55 tok/s`

而正式批量记录中的 `pp64` 是：

- `75.28 tok/s`

更合理的解释不是“其中一条一定错了”，而是：

- 当前设备温度、唤醒状态和运行顺序仍然会影响结果；
- `r=1` 只能作为最小基线，还不能作为强方差结论；
- 后续如果要把 `Qwen3 qnn-npu prefill` 用作正式比较，应至少补：
  - `r>1`
  - 固定亮屏状态
  - 更稳定的热状态控制

### 2. `LLAMA_BENCH_FAST_EXIT=1` 仍然是 bench-only workaround

这轮所有结果都统一使用：

- `LLAMA_BENCH_FAST_EXIT=1`

原因不是为了提速，而是为了绕过第二设备上已知的退出期 QNN runtime finalizer 崩溃。

因此当前结果的意义是：

- bench 输出已经稳定可采；
- 但它不是对底层 QNN runtime finalizer 问题的根因修复。

## 当前结论

截至这轮实验，第二设备 `fd8657d6` 上已经可以给出更严格的非功耗结论：

1. `Qwen2-0.5B` 和 `Qwen3-1.7B-Q8_0` 在 `Decode/Prefill` 两条路径上的 static baseline 最强后端都是 `GPUOpenCL`
2. 文档里的 `qnn-npu` baseline 必须区分两类：
   - static non-AoT `qnn-npu`
   - QNN AoT full-graph
3. `Qwen2-0.5B` 上，static non-AoT `qnn-npu` 常常只是在 CPU 附近波动，但 `QNN AoT full-graph` prefill 已重新验证到 `4280.48 / 4565.30 tok/s`
4. `Qwen3-1.7B-Q8_0` 上，当前拿到的 `qnn-npu` 仍只有 static baseline；设备侧尚缺 full-graph AoT 产物，不能直接给出 full-graph AoT 吞吐结论

这进一步强化了当前主线叙事：

- 需要研究的是阶段异构性、不同 operating points 与 runtime overhead；
- 而不是简单寻找“单一静态最强后端”。

## 下一步建议

基于这轮第二设备数据，后续更有价值的工作顺序是：

1. 把这组第二设备数据拆成两类使用：
   - `Qwen2/Qwen3` static baseline
   - `Qwen2` full-graph AoT sanity check
2. 若要补 `Qwen3` full-graph AoT，先补齐设备侧 AoT 产物
3. 回到 `Decode` 主线，补：
   - `phase × stage × backend` latency 矩阵
   - `attn_proj -> attn_core`
   - `attn_core(attn_out) -> ffn`
   边界 overhead 分解
4. 等用户把 USB 供电/亮屏/功耗采集环境收稳后，再补：
   - `Qwen2/Qwen3`
   - `CPU / GPUOpenCL / qnn-npu`
   的功率/能耗数据

在这些工作完成前，第二设备当前最稳妥的定位仍然是：

- **可用的性能对照设备**
- **不是正式功耗设备**
- **也不是当前 AoT stage 结论的主证据设备**
