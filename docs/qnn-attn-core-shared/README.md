# QNN `attn_core` Shared-Host Worklog

更新日期：2026-03-23

## Story anchor

Decode is the primary focus, so the narrative stays on the `attn_proj / attn_core / ffn` split and how those boundaries trade latency/SLO compliance against runtime overhead. The shared-host path is intended to eliminate redundant activation copies without breaking the decode SLO (single-threaded, single-batch, ctx=2048), so any conclusion must show which stage/back-end pairing is viable under that constraint and what overhead remains.

## Stage-level issues and runtime overhead to quantify

- The main prefill question is no longer “can split prefill run at all?” but “which runtime overhead dominates the remaining `1.70x` warm slowdown?” The trace-backed evidence points to three likely contributors: `72` graph launches instead of one transformer call, repeated cross-stage tensor copies because most fragment IO cannot be direct-bound, and per-layer shared-host KV writeback/materialization in `attn_core`.
- The new event-level prefill decomposition narrows that question further. At the scheduler-visible level, split prefill is not paying a meaningful explicit-copy bill; the dominant gap sits inside the single large `qnn-npu` region that expands to `24 x attn_proj + 24 x attn_core + 24 x ffn` inside QNN. That shifts the immediate optimization target away from outer scheduler memcpy and toward graph coarsening, higher direct-bind hit rate, and lower shared-host materialization pressure.
- The new ideal-vs-actual cut also narrows the scheduling story. On the current main device, stage-local upper bounds are not a single stable number: `Prefill p16` suggests a large heterogeneity upside, but matched `Prefill pp128` mostly collapses that upside, and `Decode p16` already leaves almost no `CPU/qnn` mixing headroom. That makes scale selection and route purity more important than chasing an abstract “ideal mix” in isolation.
- The new microbenchmark cross-check narrows the copy story as well. On this device, `host -> OpenCL` shared-host versus memcpy deltas are tiny relative to the tens-of-milliseconds system gaps, which matches `P4-1/P4-2`. But the reverse direction is a warning sign: raw shared-host readback is not correctness-equivalent to memcpy, so any real system path that needs correct device-to-host visibility may still pay materialization or coherence costs that the outer scheduler does not label as `tensor_copy`.
- The new formal matrix narrows the scheduling story one step further. The most stable statement is no longer “stage X likes backend Y”, but “which stage tendencies survive scale/runtime changes and which collapse when the prompt gets longer or the runtime family changes.” In practice, that means `KV_Cache` is the cleanest early cost-table entry, while `Prefill Attn_Core` and `FFN_Block` still need scale-conditional handling instead of a fixed winner.
- Cold-start variance is a separate problem from steady-state throughput. Split prefill still has to lazy-load `72` `batch=128` binaries on first touch, whereas the full-graph route loads only `transformer + lm_head`. That portion is fixable with prewarm/eager preload or by separating decode and prefill runtimes, but it does not explain the entire warm gap.
- Split prefill traces still need careful accounting because the last layer is not represented as a symmetric `128`-token FFN stage. The root cause is now understood as output-tail semantics rather than matcher breakage, so future accounting should tag that fragment separately instead of treating it as a correctness blocker.
- On the secondary device, the static `qnn-npu` baseline no longer dies in scheduler reserve, but it still relies on `qnn-npu-host` KV placement to keep `SET_ROWS/GET_ROWS` on a host-visible buffer (`tmp/fd8657d6_qnn_npu_decode_tg1_verbose_after_kvhost.log`). That keeps the route measurable, but it also means the current `tg128` includes extra overhead and cannot yet be treated as ideal single-backend NPU parity.
- The duplicate `qnn-npu` free symptom is gone after the `llama-context` backend dedup patch (`tmp/fd8657d6_qnn_npu_decode_tg1_verbose_after_ctxdedup.log`), but the exit-time abort root cause sits deeper in `libQnnHtpPrepare.so` finalization (`tmp/fd8657d6_crash_logcat_after_ctxdedup.log`). The current benchmark workaround is `LLAMA_BENCH_FAST_EXIT=1`, which skips the problematic finalizer path only after the results have already been flushed.
- The first same-scale `CPU / qnn-npu` stage-profiler runs make the next bottleneck choice clearer. For decode, static `qnn-npu` is not mainly losing on `Attn_Proj`; it is losing on `Attn_Core` and `FFN_Block`. For prefill, `FFN_Block` is already the one stage where static `qnn-npu` clearly beats CPU, which is exactly the kind of stage-local asymmetry the scheduler narrative needs. The missing column is still `GPUOpenCL`, and that gap is now a concrete memory-allocation blocker rather than an unexplained test omission.

## Minimal plan and missing evidence

- **Minimal validation**: done for `db6c02cf` prefill. The split `batch=128` route now runs end-to-end as a real fragment-chain AoT path, so the next question is no longer correctness-only.
- **Runtime-overhead reduction**: the immediate fix target is to reduce the warm `pp128` gap by increasing direct-bind hit rate or coarsening graph families so `attn_proj -> attn_core -> ffn` boundaries do not force repeated device-to-device copies and shared-host KV writeback on every layer.
- **Cost signals**: capture per-stage timings or profiler dumps that separate graph launch, cross-stage copy, and KV writeback costs. Without those measurements, we can only say there is a measured end-to-end gap, not which sub-overhead dominates.
- **Static baseline**: the reserve-time conflict is fixed for static `qnn-npu`, but the next step is still to separate “host-visible KV management overhead” from the remaining `libQnnHtpPrepare.so` exit-time corruption and from the unstable AoT decode path on `fd8657d6`.
- **Success/failure markers**: success is now a split prefill route that remains end-to-end correct while materially closing the warm `pp128` gap against full-graph AoT and preserving the decode-centric stage boundaries. Failure is either (a) paying enough copy/sync/KV overhead that split stays far slower than full graph, or (b) leaving the secondary-device AoT path unstable enough that it cannot support reproducible baseline collection.

## What still needs to be measured

1. Per-stage timing or profiler evidence showing how much of the split warm-gap comes from graph launch overhead, how much from stage-boundary copies, and how much from shared-host KV writeback/materialization.
2. A coarser-grain AoT experiment (`attention` or `transformer` families, or stronger direct-bind) showing whether the measured `41.2%` warm slowdown can be materially reduced without giving up the stage-centric scheduler hook points.
3. Energy/power logs when the device is kept awake during baseline runs so that brightness/backlight states do not mask runtime overhead or token gaps.
4. A proper root-cause fix for the `libQnnHtpPrepare.so` exit-time corruption, plus a stable AoT decode path on `fd8657d6`, so the secondary device no longer needs the bench-only fast-exit workaround or falls over before useful stage data is produced.
